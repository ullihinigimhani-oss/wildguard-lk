# Park Manager Create Patrol — implementation report

1. **Files changed.** Added `web/src/components/patrol/{PatrolMap.jsx,PatrolRoutePlanner.jsx,PatrolRoutePlanner.css,routePlanning.js}`, `backend/src/validators/plannedRoute.validator.js`, the additive migration, and route tests. Updated the manager creation form, constants, manager details page, Leaflet dependency/lockfile, Prisma schema, patrol validator/repository, existing creation tests, generated-client checks, and rollback-only live verification script.
2. **Map library/provider.** Leaflet 1.9.4 with HTTPS OpenStreetMap standard tiles and visible attribution. No API key. Provider policy: https://operations.osmfoundation.org/policies/tiles/ . Leaflet documentation: https://leafletjs.com/ . No prefetching, bulk downloads, offline tile cache, or geolocation access was introduced.
3. **Provider choice.** Fits the existing React/Vite stack, supports real geographic tiles, pan/zoom, draggable markers and polylines without billing credentials. Map rendering is separate from route editing and payload helpers. Standard OSM tiles suit this prototype; larger deployments should choose a tile service with capacity/SLA appropriate to their traffic. Initial view is Sri Lanka because existing Park records have no coordinate fields; no park coordinates were invented.
4. **Existing PatrolWaypoint.** Previously contained id, patrolId, latitude, longitude, optional note and recordedAt. No point type, sequence, or label. Existing application code did not use waypoint rows for live GPS recording.
5. **Existing PatrolLocation.** Contains latitude, longitude, recordedAt and patrolId. Remains reserved for actual ranger GPS samples; the planner writes no PatrolLocation records.
6. **Planned storage.** A single Prisma `patrol.create` nested `waypoints.create` writes the existing assignment and all validated points atomically. Existing startLocation/latitude/longitude compatibility fields derive from the START waypoint. Optional notes and names are trimmed. Distance is derived, not duplicated in storage.
7. **Schema changes.** Added nullable waypoint `type` enum, `order` integer and `label` text; added unique `(patrolId, order)` index. Nullability preserves historical unclassified rows, including multiple null orders. These rows are retained and excluded from the new planned-route response rather than fabricated into a route.
8. **Migration.** `backend/prisma/migrations/20261007180000_planned_patrol_route/migration.sql` was inspected and deployed to the configured Neon database. Migration status confirms the schema is up to date. Prisma schema validation and client generation passed. No reset, drop, truncate, delete, reseed or DATABASE_URL change occurred.
9. **Point types.** START, CHECKPOINT, HIGH_RISK, OBSERVATION and END. Map/list symbols distinguish S, numbered checkpoints, !, O and E with shape/color differences. Point labels use text-only Leaflet tooltips to avoid HTML injection.
10. **Ordering/editing.** Zero-based persisted order is consecutive. START is inserted first and END last. New intermediate points insert before END. Only intermediate types can be changed and reordered with up/down controls. Removal renumbers orders and automatic checkpoint labels while preserving custom names. Select a point to edit name/note; drag markers to reposition. Clear requires explicit inline confirmation. Optional manual coordinates are a fallback. Fit route is explicit to avoid map jumps after each click. A read-only saved route is available on manager details; no existing patrol edit workflow existed, so none was added.
11. **Distance.** Haversine distance between consecutive coordinates, summed using mean Earth radius 6371.0088 km. Summary counts, endpoints and Approx. Planned Distance update from the draft. Dashed segments represent direct waypoint connections; the interface explains that roads, trails and terrain may produce longer paths.
12. **Backend validation.** Requires 2–100 points, exactly one START first and END last, valid enum types, consecutive integer order, finite numeric coordinates (latitude −90…90, longitude −180…180), optional label up to 200 and note up to 500 characters. Rejects malformed routes with a friendly `errors.plannedRoute` response before creating anything. Existing field, time, park and approved/active ranger validation remains. The UI retains drafts on failure and blocks duplicate submissions while saving.
13. **Manager authorization.** Existing authenticated PARK_MANAGER middleware and approval checks protect creation and manager list/details. No authorization was weakened.
14. **Assignment protection.** Existing park existence and approved active RANGER checks remain. Patrol ownership and creator references are unchanged. The existing ranger selector was not park-filtered, so its behavior is preserved. Ranger detail/lifecycle requests derive identity from the verified session and query both patrol id and rangerId; client-supplied ownership cannot override it.
15. **Details API.** Existing `GET /api/patrols/:id` and `GET /api/patrols/mine/:patrolId` return `plannedRoute` ordered by `order`, exposing only type/order/latitude/longitude/label/note. Create responses also include the route. Historical records return `plannedRoute: []`. Ranger list payloads remain compact. No duplicate route endpoint was created.
16. **Tests.** 276 backend tests, 92 web tests, and 100 mobile tests pass. Backend and web suites include valid minimal/checkpoint/mixed routes, missing/duplicate endpoints, invalid types/order/coordinates/metadata, deletion/reordering, distance, manual fallback and clear confirmation. Existing authorization, old-record loading and lifecycle tests remain. Real Neon verification creates only transaction-local test accounts and patrols, verifies ordered routes through manager and assigned-ranger detail APIs, rejects Ranger B read/start/complete manipulation, checks no GPS records, then always rolls back and confirms no test users/patrols/waypoints persist. A forced nested waypoint constraint failure in a recoverable savepoint verifies no partial patrol remains. Existing scheduled and actual timestamps and Today/Upcoming/Overdue/Completed Late calculations pass regression checks.
17. **Build/browser checks.** Web production build and Android Hermes export pass. Mobile tests pass. Browser review used the actual modular route planner with real OSM tiles: map click, point name editing, mixed markers, manual fallback, fit bounds, route polyline and calculated distance worked with zero captured console errors/warnings. The temporary local review harness was removed. Screenshot: [verified preview](<C:/Users/Lihini/Desktop/WildGuard LK/wildguard-lk/web/.vite/patrol-route-preview.png>). Web build reports a bundle-size advisory; no build failure. No credentials or map secrets were added; environment files and generated outputs remain ignored.
18. **Next phase.** Ranger mobile View Planned Route UI, current GPS location, actual route sampling, visited checkpoints, incident reporting during patrol, and planned-versus-actual comparison remain deferred as requested. This implementation prepares the owner-protected data API without adding those workflows.

## Verification commands

Backend: `npm test -- --silent`; `npx prisma validate`; `npx prisma generate`; `npx prisma migrate status`; `node scripts/verifyPatrolLifecycle.js`.

Web: `npx vitest run --configLoader runner`; `npx vite build --configLoader runner`. Runner config loading avoids the Windows sandbox esbuild config-loader directory permission issue.

Mobile: `npm test -- --silent`; `npx expo export --platform android --output-dir .expo/route-check`. Android export required permission to execute the installed Hermes compiler outside the sandbox.
