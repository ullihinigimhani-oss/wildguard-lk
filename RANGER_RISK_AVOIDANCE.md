# Ranger known-risk-zone avoidance

Verified on 2026-10-08 on `feature/ranger-patrol-incident-management`.

1. **Existing RiskZone schema:** `id`, `name`, optional `description`, `riskLevel` (LOW/MEDIUM/HIGH/CRITICAL), `isActive`, `centerLatitude`, `centerLongitude`, `radiusMeters`, `parkId`/Park relation, alerts, `createdAt`, and `updatedAt`. There is no polygon/GeoJSON field or separate type/notes field.
2. **Schema sufficient:** yes; the existing centre plus radius defines a meaningful area. Read-only inspection found **zero existing RiskZone records**. There is no implemented RiskZone management API/UI in the existing application; meaningful park risk data still needs to be provided through a future authorized management workflow.
3. **Migration required:** none. No migration was created or applied.
4. **Geometry representation:** each stored circle is converted server-side to a GeoJSON Polygon with 32 vertices plus the closing coordinate. Multiple areas produce a MultiPolygon for routing. Coordinates are longitude/latitude; the database representation stays unchanged.
5. **Relevant zones:** authoritative patrol `parkId`, active HIGH/CRITICAL zones only, stable ID ordering. Other parks, inactive zones, LOW/MEDIUM zones and warning waypoints are excluded. All applicable high-risk areas in that park are retained within the application limits rather than silently dropping inconvenient zones.
6. **Validation/conversion:** finite coordinate ranges, positive radius at most 5 km, geodesic conversion on a spherical Earth, closed/non-degenerate rings and rejection of dateline-crossing or unusable geometry. A circumscribed polygon adds approximately 0.5% plus 0.1 m to enclose the stored circle between vertices. Application limits are 32 zones, 150 km² summed area and an 18 km combined diagonal extent. Invalid active data or exceeded limits blocks navigation with a structured warning; validated areas remain available for display. These are conservative application policies, below the published provider area/extent ceilings.
7. **ORS implementation:** the existing service uses `options.avoid_polygons` only when relevant zones exist, with the existing HeiGIT `foot-walking` endpoint and backend Authorization header. No normal-route preflight or separate routing loop is added to production. Provider geometry and start/end connections are checked for zone intersections, including segment crossings where both endpoints lie outside. Cache hits and coalesced nearby origins are checked too. A changed zone/destination fingerprint invalidates reuse. Live temporary-coordinate verification returned **HTTP 200 for both normal and avoidance requests**, with non-crossing geometry and ORS distance/time. The test route increased from 1,039.1 m to 1,070.6 m. See [official routing options](https://giscience.github.io/openrouteservice/api-reference/endpoints/directions/routing-options) and [hosted restrictions](https://openrouteservice.org/restrictions/).

Existing foreground location, permissions, navigation hierarchy and map provider are retained. This report and a historical-note update to the prior phase report document the change.
10. **Map rendering:** semi-transparent red polygons with red borders in a dedicated pane below navigation/GPS/waypoint overlays. Popups show Risk Zone, saved name, risk level and description as text. Unchanged risk polygons are not rebuilt on GPS updates, preserving their open popups. Actual browser verification confirmed the popup and retained zone after a routing-unavailable update, with no JavaScript console errors. Browser OSM tiles remain blocked in this test environment; the user has separately confirmed physical iPhone tile loading. Leaflet/OpenStreetMap was preserved.
11. **Point versus area:** red `!` HIGH_RISK PatrolWaypoint markers retain their separate warning-point meaning and remain skipped as destinations. Only saved RiskZone centre/radius records create avoidance areas. No waypoint is given an invented radius.
12. **Destination inside:** backend returns `DESTINATION_IN_RISK_ZONE` before ORS. Mobile retains the destination and displays the zone/warning. Arrival checks wait for trusted risk context and do not advance over an affected point, even if GPS outside the zone is within 40 m of that point.
13. **Ranger inside:** separate `RANGER_IN_RISK_ZONE` warning. The system conservatively declines to recommend an outward route because a strictly non-intersecting route cannot start inside the polygon. It does not drop avoidance, promise a safe exit, or mark a waypoint reached. Position, zones, planned points and actual trail remain visible. The Ranger can review the position/contact the Park Manager; ordinary routing can resume after GPS is outside. Outward evacuation guidance is not implemented.
14. **No alternative:** `NO_RISK_AVOIDING_ROUTE` for unavailable/crossing avoidance results. There is no retry without avoidance and no fabricated straight navigation line. Invalid data/provider restrictions use separate structured codes; rate limits/timeouts retain their existing sanitized handling. The screen keeps zones, current GPS, actual trail and the next destination, with retry/refresh where applicable.
15. **Distance/ETA:** returned from the avoiding ORS route and updated using the existing remaining-summary calculation. A longer avoiding route's summary replaces the shorter normal route's values. Blocked/unavailable routes show no stale live distance/ETA.
16. **Off route:** existing deviation logic and automatic refresh remain; every production reroute reloads trusted park zones and supplies avoidance again. Risk context is loaded once on active navigation entry/resume for display and arrival gating, and refreshed by routing responses or explicit patrol refresh. Newly edited zone data becomes authoritative on the next server request; real-time zone-change broadcasts are not part of this phase.
17. **Quota:** existing client 20-second cooldown, three-fix deviation threshold, movement/time thresholds, one in-flight request, server cache/coalescing, server per-Ranger/process rate limits and 15-second timeout remain. Risk-aware routing uses the same ORS service and budget. No request is made on every GPS update. The existing server budget is process-local.
18. **Authorization:** Ranger role, active/approved account, assigned patrol ownership, IN_PROGRESS state, and saved waypoint ownership/type remain enforced. New owner-protected GET `/api/navigation/patrols/:patrolId/risk-zones` supplies display/arrival context. Client `options`, `avoid_polygons`, `riskZones` and `avoidanceGeometry` are rejected by POST navigation; clients cannot modify RiskZones through either endpoint.
19. **Secret:** the ORS key remains backend-only. Exact private comparison scanned **212 client source/export files with zero matches**. Both backend and mobile `.env` remain ignored; neither environment file was changed or staged. Error responses omit upstream bodies/headers, and map payloads contain no authentication material.
20. **Database/data changes:** none during implementation/verification. Only counts were read; temporary ORS areas were never saved. No existing user, patrol, waypoint, location or RiskZone record was created, changed or deleted for testing. Future real navigation continues the existing controlled PatrolLocation writes; risk avoidance never rewrites planned points or actual GPS history.
